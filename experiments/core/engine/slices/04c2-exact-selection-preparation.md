## Execution-group mechanism

The current Worker consumes function membership, path/module/export, kind,
visibility, args/returns, partition and ordinals. Existing V1 and V2 catalog frames
commit the complete ordered manifest.functions array; V2/V3 use the V2 catalog
frame. Together with the existing sourceArtifact identity this covers the actual
Worker catalog and code correlation.

The shared execution projection includes the verified catalog digest alongside
source artifact, runtime host and compatibility date. Activation and finite
preparation already receive an authenticated basis digest. Backfill derives
and verifies it through the same canonical frame owner. No new projection registry,
catalog codec, dependency key, per-call token or Worker wire method is selected.

Keep existing canonical activation and metadata sequence/tombstone handling.
Same-source child args/returns/partition, membership/ordinal and visibility
expansion change the group. Withdrawal/removal can additionally trigger existing
live revocation. ABA remains a change even when the final semantic hash returns
to its original value. Unrelated schema/table-only changes must not be added to
this execution-group preimage.

Schema-only changes have two distinct controls. A genuine read-only contribution
can retain its unchanged execution group. A contribution with row intents still
obeys its original candidate-schema validation; a newly activated candidate may
refuse that write independently of the execution group. Do not weaken that guard
to make a cache-invalidation control pass.

## Existing observations and maintenance

The generic semantic-bytes storage supports this change without a new table,
column, anchor/dependency codec or SQL format migration. Use the existing public
migrate/installation-reconciliation lifecycle and canonical Application backfill.
It authenticates the current head/manifest/catalog, initializes only the current
observations, advances changed metadata sequences, preserves unchanged contracts
and tombstones, and is idempotent. Replaying an already active publication is not
the upgrade protocol.

Coordinate replacement of affected runtime and activation-writer binaries with
that maintenance boundary. Current installation attestation does not version the
JavaScript projection algorithm, so mixed old/new writer compatibility is not
claimed. Maintenance drains admitted SQL and invalidates issued installation
capabilities; it does not delete or automatically terminalize every logical
attempt. Preserve all anchors, reservations, original watermarks, sessions and
outcomes. Old graphs must refuse or follow existing authenticated conflict,
recovery or expiry owners; maintenance never authorizes a fresh body or rewrites
old captures. Failure must leave the installation drained for its existing
successor owner.
