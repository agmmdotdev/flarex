# DTE02-E: Domain Identity Types And Ownership

## Status And Scope

**Status:** Complete identity-contract receipt. DTE02-F input/store-port and
DTE02-G final identity admission are also complete; Roadmap 03's lifecycle
model is next.

This receipt fixes the names, encoded forms, validation rules, generation
authority, equality, visibility, and scope behavior of the identities needed
by the admitted `@flarex/durable-task` run-attempt package. It also closes the
choice left by DTE02-D: task-definition revision identity is storage-issued,
not derived from a public digest.

This document does not create a package, schema, migration, table, public API,
runtime host, scheduler, or production route. Roadmap 04 still owns physical
columns, indexes, transactional SQL, collision retry implementation, and
PGlite/Postgres proof. DTE02-F now fixes the exact command and typed-error
unions that carry these values in
[`10-dte-ip01-input-and-store-port-contract.md`](./10-dte-ip01-input-and-store-port-contract.md).

## Decision Summary

The accepted private V1 identities are:

| Meaning | Type | Canonical encoded form | Owner |
| --- | --- | --- | --- |
| stable developer task key | `TaskIdV1` | validated developer text | Standard Application task catalog |
| immutable definition binding | `TaskDefinitionRevisionIdV1` | `taskdef_<lowercase UUIDv4>` | Task System binding registration |
| durable run history | `TaskRunIdV1` | `run_<lowercase UUIDv4>` | Task System run creation |
| attempt history | `TaskAttemptIdV1` | `attempt_<lowercase UUIDv4>` | Task System attempt creation |
| retry-policy ordinal | `TaskAttemptNumberV1` | positive safe integer | Task System lifecycle transaction |
| execution ownership generation | `TaskExecutionFenceV1` | positive signed-64-bit integer; canonical decimal text at encoded boundaries | Task System claim transaction |

The three generated string IDs use one canonical value each. There is no
Trigger-style internal CUID plus friendly ID pair. None of the identifiers
contains tenant, project, environment, deployment, scope, epoch, storage
generation, region, physical locator, queue partition, or compute placement.

All task-system identities are scope-local lookup values. Their random bodies
make accidental collision extremely unlikely, but global uniqueness is not an
authority claim. A scope-bound Task System capability must select the scope
before any identity is looked up.

## Source-Reuse Decision

### Trigger Semantics Retained

The frozen Trigger source remains the compatibility oracle for these useful
semantics:

- a developer task ID is stable across deployments/revisions;
- run and attempt identities are distinct;
- `run_` and `attempt_` prefixes make logs and API values self-describing;
- an attempt ID names history rather than execution ownership;
- ID generation is not delegated to user task code; and
- malformed or colliding identities must not silently select another row.

Trigger collision, round-trip, duplicate-task-ID, and malformed-ID scenarios
remain test inputs. The exact generated byte strings are not compatibility
targets because Flarex deliberately changes the identity authority.

### Trigger Mechanics Discarded Or Seam-Adapted

Trigger's `IdUtil` creates both a database CUID and a separate prefixed
friendly ID. Flarex keeps one canonical prefixed ID. Accepting either form
would create aliases, ambiguous equality, and a legacy lookup path.

Trigger's newer run-ops ID combines a 48-bit wall-clock millisecond value,
72 random bits, a region character, and a format character in a 26-character
base32hex body. Its parser uses that body to choose Trigger's legacy or
partitioned table and its tests bind the shape to residency and Kubernetes pod
names. Those are Trigger product-routing and compute-host concerns. They
conflict with these Flarex rules:

- database state, not ID lexicographic order, owns lifecycle ordering;
- trusted scope capability, not an ID character, owns storage routing;
- runtime binding and compute policy, not an ID character, own placement;
- a malformed current ID must fail rather than become a legacy lookup; and
- one durable identity must survive host and provider changes.

Therefore the base32hex encoder/decoder, embedded timestamp, region code,
residency parser, Kubernetes delimiter contract, nanoid alphabet, CUID body,
and legacy fallback are not admitted. This is the justified reimplementation
boundary: adapting those mechanics would preserve authority Flarex must
remove.

The replacement reuses the repository's established persistence-owned
`crypto.randomUUID()` generation pattern and canonical lowercase UUID
validation mechanics. It does not import the existing protocol identity types.

## Canonical Validation Contracts

### Shared Generated-ID Body

`TaskDefinitionRevisionIdV1`, `TaskRunIdV1`, and `TaskAttemptIdV1` each contain
one canonical lowercase RFC 4122 UUID version 4 body:

```text
xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx
```

Every `x` is one lowercase hexadecimal character and `y` is one of `8`, `9`,
`a`, or `b`. The full validators are equivalent to these anchored patterns:

```text
TaskDefinitionRevisionIdV1
^taskdef_[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$

TaskRunIdV1
^run_[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$

TaskAttemptIdV1
^attempt_[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
```

Uppercase hexadecimal, missing hyphens, braces, URNs, bare UUIDs, CUIDs,
nanoids, Trigger legacy IDs, a wrong prefix, a non-v4 UUID, whitespace, or an
otherwise plausible suffix is invalid. A decoder never trims, lowercases,
adds a prefix, converts a Trigger internal ID, or falls back to another parser.

The future `@flarex/durable-task` internal subpath owns Effect Schema values
with these exact names:

- `TaskDefinitionRevisionIdV1Schema` branded as
  `FlarexDurableTask/TaskDefinitionRevisionIdV1`;
- `TaskRunIdV1Schema` branded as `FlarexDurableTask/TaskRunIdV1`; and
- `TaskAttemptIdV1Schema` branded as
  `FlarexDurableTask/TaskAttemptIdV1`.

The schemas are validators and nominal type owners. They expose no production
mint function. Fixed schema-made values are permitted in package-local tests;
that test convenience is not production generation authority.

### `TaskIdV1`

`TaskIdV1` remains owned by the canonical Standard Application task catalog,
not by the run-attempt package. Its private V1 validator accepts a value only
when all of the following are true:

1. it is a primitive JavaScript string;
2. it is valid Unicode scalar text with no unpaired surrogate;
3. its UTF-8 representation is between 1 and 255 bytes inclusive;
4. it contains no C0 or C1 control character, including PostgreSQL's forbidden
   null byte; and
5. its first and last code points are not ECMAScript whitespace.

The validator does not trim, lowercase, case-fold, NFC/NFKC-normalize, decode
a URL, or interpret `/`, `.`, `:`, `_`, or `-`. Internal whitespace and visible
Unicode are allowed. The accepted spelling is the canonical spelling and is
preserved byte-for-byte in the canonical task manifest.

Duplicate detection occurs after validation and uses exact string equality.
`invoice.send`, `Invoice.Send`, and `invoice/send` are three different task
IDs. A future public SDK may offer an ergonomic producer, but it must emit this
same private value and may not create an aliasing normalization layer.

The 255-byte bound is a private V1 catalog/index contract, not a claim that
Trigger has the same bound. Widening it later requires a new reviewed contract
and storage/index proof; no current compatibility consumer requires arbitrary
unbounded task ID text.

### `TaskAttemptNumberV1`

`TaskAttemptNumberV1` is a branded JavaScript number. It accepts only a
positive safe integer. The first policy-counted attempt is `1`. Zero, negative
values, fractions, infinities, `NaN`, numeric strings, bigint values, and
unsafe integers are invalid.

Attempt number is descriptive retry-policy state. It is not a lease token and
must not be used to authorize heartbeat or completion. A recovery or ownership
change may advance the execution fence without pretending the ordinal itself
is an authority token. Roadmap 03 fixes which lifecycle transitions consume a
retry attempt and therefore advance this number.

The future package owns `TaskAttemptNumberV1Schema`, branded as
`FlarexDurableTask/TaskAttemptNumberV1`.

### `TaskExecutionFenceV1`

`TaskExecutionFenceV1` is a branded bigint whose valid range is:

```text
1 <= fence <= 9223372036854775807
```

The in-memory domain type is `bigint`. The Postgres representation is a
positive signed `bigint`. Any JSON, canonical command frame, durable intent,
or worker-dispatch encoding represents it as canonical base-10 text:

```text
1
2
9223372036854775807
```

Encoded zero, a sign, leading zero, decimal point, exponent, surrounding
whitespace, non-decimal digit, or out-of-range value is invalid. A JavaScript
number is never accepted at an encoded boundary because values above the safe
integer range would lose authority evidence.

The future package owns `TaskExecutionFenceV1Schema`, branded as
`FlarexDurableTask/TaskExecutionFenceV1`. Its encoded side is canonical decimal
text and its decoded side is bigint. Fence exhaustion is terminal and must
never wrap, clamp, reset, or reuse an older value.

## Generation And Storage Authority

### General Rule

Generated IDs are output from Task System operations, not caller-controlled
command fields. The Postgres adapter mints candidates through its injected
random-UUID capability, whose production default is `crypto.randomUUID()`.
Generation happens as part of the owning persistence operation so an ID is not
observable as accepted until the corresponding row is committed.

The domain service receives already validated IDs in store receipts and sends
them back only in commands that act on existing state. User task code, public
request bodies, queues, and compute providers do not mint authoritative IDs.

For every generated ID:

1. the adapter obtains a UUID candidate;
2. it validates the candidate as canonical UUIDv4 before prefixing;
3. it constructs and validates the prefixed domain ID;
4. it inserts under the already selected scope and owning transaction; and
5. it returns the ID only from the committed receipt.

A malformed injected/random candidate is a generation/configuration failure,
not invalid user input. A true ID collision with a different row is never a
replay signal. The adapter makes at most three candidate attempts in the same
logical operation and then fails with typed collision-exhaustion evidence.
Unknown random-source failures retain their cause at the persistence boundary.
DTE02-F and Roadmap 04 fix the concrete tagged error names without weakening
these distinctions.

### Task-Definition Revision

`TaskDefinitionRevisionIdV1` is issued by the Task System binding-registration
operation after DTE02-D's full `TaskDefinitionRuntimeBindingV1` has been
validated under fresh scope authority.

It is deliberately storage-issued rather than content-addressed. The ID is an
opaque row identity, while canonical binding fields and digests remain the
integrity and idempotency evidence. This avoids:

- presenting a digest prefix as proof that the binding was accepted;
- leaking or correlating canonical binding content through an ID;
- coupling the domain package to application/runtime canonical codecs; and
- making a future physical normalization change alter the public spelling.

Identical binding replays still converge. Roadmap 04 must enforce one unique
semantic binding key under the scope, covering every field admitted by
DTE02-D. A find-or-insert replay or concurrent losing insert returns the
winner's existing `TaskDefinitionRevisionIdV1`. A different binding cannot
reuse that row. UUID collision handling is separate from semantic-binding
convergence.

The persisted definition row is keyed or uniquely constrained by both scope
and revision ID. The ID is not globally resolved and does not carry the scope.

### Run

`TaskRunIdV1` is issued inside the idempotent new-run creation transaction.
The caller supplies the permitted task/input/idempotency intent; it does not
supply the run ID.

An idempotency replay with the same canonical request returns the already
committed run ID. A conflicting request returns the idempotency conflict and
does not mint a replacement. A lost response followed by replay therefore
cannot create a second run merely because another random candidate is
available.

Run ordering comes from authoritative stored creation time, run version, and
ordered-event evidence. Code must never sort or route runs by parsing UUID
bits or by assuming generation order from the ID.

### Attempt And Fence

`TaskAttemptIdV1` is issued when the Task System transaction creates a new
attempt-history record. `TaskAttemptNumberV1` is allocated from the run's
retry-policy state. `TaskExecutionFenceV1` is allocated from the run's
monotonic execution-ownership state.

The same transaction that grants execution must atomically:

- lock or conditionally compare the authoritative run state;
- allocate the next valid fence greater than every fence previously granted
  for that run;
- create or select the attempt-history record required by Roadmap 03;
- persist the lease and accepted fence; and
- return attempt ID, attempt number, fence, and lease evidence together.

The random attempt ID does not authorize execution. The attempt number does
not authorize execution. The accepted fence plus current durable lease and
state does. Heartbeat, completion, retry commitment, and cancellation
acknowledgment must compare the supplied fence with current authoritative
state inside their transaction.

Roadmap 03 decides whether a particular recovery transition creates a new
attempt-history row or renews/replaces ownership within an existing history
record. It cannot relax the rule that every new execution grant advances the
fence and stale fences fail closed.

## Equality, Aliasing, And Lookup

Generated string identity equality is exact JavaScript string equality after
successful decoding. Task ID equality is exact accepted spelling equality.
Attempt number equality is numeric equality on validated safe integers. Fence
equality is bigint equality.

No identity has:

- case-insensitive equality;
- prefixless equality;
- UUID-only equality;
- internal-versus-friendly aliases;
- legacy/current aliases;
- normalization before comparison; or
- equality inferred from a display label, URL, digest, timestamp, or row
  position.

Equal ID text alone does not prove equal authority. The same ID text may exist
under two scopes, and even a globally unlikely UUID collision cannot cross the
scope-bound store. A definition revision ID also does not prove its binding;
the persistence owner loads and validates the stored binding before execution.

Every lookup begins from an issuer-backed, scope-bound Task System capability.
There is no production `findRunGlobally(runId)`, `findAttemptGlobally`, or
`findDefinitionGlobally` operation. An ID presented under the wrong scope is
reported through the same non-disclosing unavailable/not-found behavior as an
absent ID. It must not reveal the owning tenant, scope, application, task,
artifact, or existence of a cross-scope row.

## Opaque, Serializable, And Visible Boundaries

"Opaque" means nominal and uninterpreted by the run-attempt domain. It does
not mean non-serializable, secret, globally authoritative, or safe to use
without authorization.

| Value | Serializable use | Visibility rule |
| --- | --- | --- |
| `TaskIdV1` | canonical task manifest, authorized invocation input, safe read model | developer-visible after application/scope authorization |
| `TaskDefinitionRevisionIdV1` | trusted stored binding and internal run receipts | internal in the first vertical; no ordinary UI/API projection |
| `TaskRunIdV1` | task commands, wakes, events, internal and later authorized API locators | may become developer-visible, but never bypasses scope authorization |
| `TaskAttemptIdV1` | task commands, execution receipts, events, authorized attempt projection | may become developer-visible with the parent run authorization |
| `TaskAttemptNumberV1` | lifecycle receipts and authorized attempt projection | descriptive only |
| `TaskExecutionFenceV1` | trusted store commands, durable effects, dispatch and completion protocol | excluded from ordinary read models, URLs, logs, traces, and user code |

Queue and wake messages may carry `TaskRunIdV1` and a bounded wake/version
hint, but their possession is not authority. The consumer reacquires the
scope-bound store and loads current durable state. A dispatch/completion
protocol may carry a fence because the receiver must compare it, but logs and
errors must not expose the value unnecessarily.

No serialized task-domain command may add raw tenant, project, environment,
deployment, scope, epoch, storage generation, storage-generation fence,
physical locator, region, or runtime artifact URL beside these IDs. Those
values remain out-of-band capabilities or persistence-owned evidence under
DTE02-C and DTE02-D.

## Validation And Error Behavior

The same schemas may validate values at more than one boundary, but the owner
maps failure according to the evidence source:

| Source of invalid value | Required behavior |
| --- | --- |
| private task definition contains invalid `TaskIdV1` | deterministic task-definition validation failure before registration |
| untrusted/internal request contains malformed run or attempt ID | typed command-validation failure before store access |
| queue/wake contains malformed ID | reject or dead-letter under host policy; do not probe storage |
| generated UUID candidate is malformed | persistence generation/configuration failure |
| generated ID collides with a different row after bounded retries | persistence collision-exhaustion failure |
| stored row contains malformed ID, attempt number, or fence | task-state corruption; never ordinary not-found or user error |
| well-formed ID is absent under selected scope | non-disclosing unavailable/not-found result |
| well-formed ID exists only under another scope | exactly the same non-disclosing result |
| supplied fence differs from current accepted fence | stale-execution result; no mutation and no existence disclosure beyond the authorized run context |
| fence would exceed signed-64-bit maximum | terminal fence-exhaustion failure; never wrap or reset |

DTE02-F now fixes the concrete tagged error union in
[`10-dte-ip01-input-and-store-port-contract.md`](./10-dte-ip01-input-and-store-port-contract.md).
It preserves these categories rather than collapsing corruption, stale
execution, invalid command, generation failure, scope mismatch, or absence
into a generic `Error`.

Schema parse diagnostics are boundary detail, not a stable public API. Safe
errors may name the expected identity kind and canonical format, but must not
echo secrets, cross-scope row evidence, binding contents, or raw infrastructure
causes.

## Existing Flarex Authorities Not Duplicated

### Application And Runtime Identity

`TaskDefinitionRevisionIdV1` is not an application revision ID, deployment ID,
candidate digest, task-catalog digest, application-revision task-binding
digest, runtime-target digest, artifact ID, or object-store key. It names the
Task System's accepted immutable binding row. DTE02-D's digests prove content;
the storage-issued ID locates the accepted binding under scope.

### Scope And Storage Identity

No task identity replaces or wraps `ScopeId`, `ReplacementScopeIdV1`, scope
epoch, storage generation, storage-generation fence, or physical locator.
Those remain persistence/control-plane authorities carried by the scope-bound
capability, never by the ID.

### Transaction Session Identity

`TaskRunIdV1` is not `TransactionSessionIdV1`. A task run may span many worker
invocations and user-code database transactions; a transaction session owns a
bounded application-data mutation protocol. Reusing the session ID type would
couple unrelated lifecycles and suggest authority the run does not possess.

`TaskExecutionFenceV1` is not `TransactionAttemptFence`. The two values share
the same positive signed-64-bit representation because both must round-trip
through Postgres and JSON safely, but their authorities are disjoint:

- transaction attempt fence authorizes one application-data transaction
  session attempt; and
- task execution fence rejects stale durable-task execution ownership.

The task package therefore defines its own Effect Schema using its admitted
`effect` dependency. It does not import `flarex-protocol`, copy a protocol
brand, or expose either fence as the other. Shared wire mechanics do not make
two domain authorities interchangeable.

### Trigger Identity

The prefixes do not claim Trigger API compatibility. A Flarex `run_...` or
`attempt_...` value is never sent through Trigger's `IdUtil`, `parseRunId`,
legacy table selection, residency classification, or internal-ID conversion.
The frozen workspace remains a source/test oracle only.

## DTE-IP01 Package Consequences

The admitted internal subpath remains:

```text
@flarex/durable-task/internal/run-attempt-v1
```

It may define and export only within that private surface:

- `TaskDefinitionRevisionIdV1Schema` and type;
- `TaskRunIdV1Schema` and type;
- `TaskAttemptIdV1Schema` and type;
- `TaskAttemptNumberV1Schema` and type; and
- `TaskExecutionFenceV1Schema` and type.

`TaskIdV1` stays with the future canonical task-catalog owner and does not need
to enter DTE-IP01 commands. The host resolves task ID to a validated immutable
definition revision before invoking run creation.

The package needs no new dependency. Its exact generated-ID patterns and
fence/number schemas can be expressed through the already admitted `effect`
runtime. It must not import:

- `flarex-protocol` or one of its identity/fence schemas;
- `@flarex/persistence-postgres` or Drizzle types;
- Node crypto or Cloudflare crypto merely to mint an ID;
- Trigger core, `nanoid`, or `@bugsnag/cuid`; or
- application-revision, scope-authority, artifact, or runtime-publication
  types.

Production ID generation remains behind the broader Task System persistence
owner. DTE02-F keeps new-run creation outside the narrow DTE-IP01 service and
makes attempt-claim commands omit caller-generated attempt IDs and fences;
store receipts return the accepted grant. See
[`10-dte-ip01-input-and-store-port-contract.md`](./10-dte-ip01-input-and-store-port-contract.md).

## Required Proofs For Later Roadmaps

DTE-IP01 package tests must prove:

1. every accepted generated ID matches exactly one kind;
2. uppercase, bare, wrong-prefix, non-v4, Trigger CUID/nanoid, run-ops v1, and
   malformed values fail;
3. no decoder normalizes or falls back;
4. attempt number and fence representations reject coercion and range errors;
5. schemas are nominally distinct at compile time; and
6. the private subpath compiles and bundles with only `effect`.

Roadmap 04 adapter tests must additionally prove:

1. definition-binding replay and concurrent insertion converge on one stored
   revision ID;
2. run idempotency replay returns the original run ID after a lost response;
3. a conflicting idempotency request does not mint a second run;
4. competing attempt grants produce distinct IDs and strictly increasing
   fences;
5. a stale fence cannot heartbeat, complete, retry, or acknowledge
   cancellation;
6. fence exhaustion fails without wraparound;
7. malformed stored identities are corruption;
8. collision retries are bounded and never mistaken for idempotency replay;
9. scope A cannot load scope B's definition, run, or attempt by ID; and
10. PGlite and real Postgres agree on stored identity and bigint behavior.

Observability/API roadmaps must prove that run and attempt locators are always
scope-authorized and that fences and internal definition revision IDs are not
leaked by ordinary projections.

## Explicit Non-Goals

DTE02-E does not authorize:

- a root/public task identity export;
- a public task SDK or Trigger API compatibility endpoint;
- global run lookup or global ID uniqueness as authorization;
- UUIDv7, ULID, CUID, nanoid, run-ops base32hex, or database-sequence IDs;
- parsing timestamps, region, residency, shard, or placement from an ID;
- a legacy ID migration or fallback parser;
- content-addressing task-definition revision IDs;
- task tables, schema migrations, indexes, or SQL;
- user-supplied run IDs, attempt IDs, or fences;
- logging or UI projection of the execution fence;
- using attempt number as a fence; or
- production activation.

## Decision Receipt

DTE02-E is complete with these conclusions:

1. `TaskIdV1` remains the exact, scope-local developer key owned by the
   Standard Application task catalog;
2. `TaskDefinitionRevisionIdV1`, `TaskRunIdV1`, and `TaskAttemptIdV1` are
   distinct branded strings with `taskdef_`, `run_`, and `attempt_` plus one
   canonical lowercase UUIDv4 body;
3. the Task System persistence operation, not the domain service or caller,
   mints each generated ID;
4. definition IDs are storage-issued and converge through the unique canonical
   binding key rather than exposing a content-derived ID;
5. `TaskAttemptNumberV1` describes retry policy while
   `TaskExecutionFenceV1` authorizes the current execution grant;
6. the execution fence is a positive signed-64-bit bigint and uses canonical
   decimal text at encoded boundaries;
7. all IDs are scope-local, carry no scope or placement data, and are looked up
   only through the scope-bound Task System capability;
8. malformed, absent, cross-scope, colliding, corrupt, stale, and exhausted
   cases retain distinct failure meanings;
9. Trigger's semantic identity separation and prefixes are retained, while its
   dual IDs, CUID/nanoid bodies, run-ops routing format, and legacy parser are
   discarded for explicit authority reasons;
10. existing Flarex application, scope, transaction-session, and transaction-
    fence authorities remain distinct; and
11. DTE-IP01 can define the approved run-attempt identity schemas with its
    admitted `effect` dependency only; DTE02-F and DTE02-G are now complete,
    and Roadmap 03 is next.
