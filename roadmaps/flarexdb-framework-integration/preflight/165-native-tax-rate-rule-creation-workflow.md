genuine `createTaxRateRulesStep`, and the retained physical Rule deletion inverse.

`48d5cc675e4e8bc821e22c20c88a751acc66fb5f`.

The bounded Rule creation profile also admits repeated supplied IDs within one
fresh batch. Shared scalar planning preserves every native response position

## Connected native contract

The workflow returns the complete native Rule array. Its step resolves Tax and
calls `createTaxRateRules` even for an empty input. It retains returned Rule IDs;
empty compensation skips resolution, while nonempty compensation calls genuine
physical `deleteTaxRateRules`. The separate `deleteTaxRateRulesWorkflow` uses
soft deletion and restore and is outside this branch.

The Tax service's own `createTaxRateRules` wrapper preserves scalar/array
normalization and serialization around the native internal Rule create service.
Manager/event decorators, repository persistence and generated physical deletion
remain part of the closure. The complete four-model Tax DML stays installed.
Rules have required Rate, `reference` and `reference_id` values, nullable creator
and metadata, managed identities/timestamps and active uniqueness on
`(tax_rate_id, reference_id)`. The reference name does not weaken that key.
References are strings; this root does not resolve Products, Product Types or
Shipping Options. Rule deletion must preserve parent Rates, Regions and Providers.

Standalone Rule creation preserves its own creator; it does not inherit or
overwrite the creator from the parent Rate. Native empty/null/default behavior,
managed fields, complete immediate/cold DTOs, events and parent-reference behavior
must come from the executing baseline, not assumptions from nested Rate creation.

The original maximum creates eight Rules across four existing Rates. With IDs
deliberately reversed, returned Rules and creation events follow input order;
retained physical deletion events follow creation order. Native SQL
`DELETE RETURNING` supplies no general order guarantee. Any portable Rule-root
ordering proposal needs its own explicit decision and separately labeled proof.

The original array branch accepts general JSON metadata, supplied managed values
and Rule-local creators; active/deleted reference constraints and parent foreign
keys retain native database behavior. A deleted Rate remains a valid reference.
Repeated native transaction IDs execute the create again and encounter active
uniqueness, which is distinct from trusted durable replay. A committed Rule is
independently consumed by the genuine item-tax-lines calculation.

Outside the array workflow contract, `{ rules: singleObject }` reaches the native
scalar service and commits a Rule before the step's `created.map` fails. That
original failure and remaining row/event are preserved. The selected profile
requires the declared array shape; no native scalar-input correction is proposed.
Unknown scalar fields are ignored natively and explicitly refused by the bounded
candidate. Diagnostic container-resolution observations are incomplete, so the
genuine step source and observed native calls establish the resolution branch.

The approved portable inverse selects the complete retained Rule cohort by
authenticated storage insertion order and uses the existing physical graph
receipt. Its controls bind ordered identities, selector, counts, complete writes,
preimages and deletion events. This Rule-root ordering has its own explicit
approval and remains separate from the original unordered-SQL witness. Other
profiles retain their existing ordering.

## Bounded admission

The separate `tax.ruleCreate` profile admits zero to eight Rules across at most
four existing Rates. Forward creation and the retained physical inverse preserve
the default 64 calls, 64 events and other resource limits. Only the existing
trusted outer owner settles the root. Calculation and Rate creation grants remain
distinct; Rate, Region and Provider repositories are denied in this profile.

The exact native root and step use the existing portable workflow runtime and
source-pair/callback verifiers. Complete native DTOs, Rule-local creators, general
JSON metadata, supplied managed values, empty calls, native events and the
retained created-ID cohort are preserved. Physical deletion keeps parent and
unrelated rows intact, including Rules created after the original run.

Tax construction, shared scalar insertion, checked managed values, event capture,
authenticated receipts and physical lifecycle owners are reused. Complete row
and default compilation derives from the same checked Tax DML for both creation
profiles. Full output authentication binds every Rule field and response
position to the canonical SQL write, observed row and event. Repeated positions
require explicit supplied identity sharing and equal complete DTOs; generated
identities remain distinct. Inverse authentication binds complete selected
identities, writes and events without re-executing native business calls.

Late foreign defects retain their complete Cause and original identity under the
accepted [Promise/Cause contract](./161-native-promise-cause-preservation.md).
Constraint failures, corrupted native outputs and conflicting trusted replay do
not publish a partial graph. Trusted durable replay remains separate from the
original native transaction-ID repetition behavior.

Tax Region/provider bootstrap, Rule soft-delete/restore, Rule replacement, Rate
updates, complete Cart admission, remote providers, File import/export,
performance acceptance and hosted/production activation remain outside this root.
