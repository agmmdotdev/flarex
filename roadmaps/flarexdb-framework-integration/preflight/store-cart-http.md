# Store Cart creation and retrieval HTTP

Status: implemented private Store Cart creation and retrieval HTTP profile.

## Scope and source challenge

Promote pinned `POST /store/carts` and `GET /store/carts/:id` through the private
Effect HTTP and actual Workerd application DO. Reuse the genuine native
eighteen-source Cart creation workflow, its authenticated graph, existing Core
storage and sole settlement owner. Other Cart mutations and checkout HTTP remain
outside this slice. No named durable dataset is migrated or reset.

Two independent readers challenged current executing owners, accepted direction
and pinned Convex `db914cf06e2b06ee985646611b9e12ed7a770318`, then exchanged
counterexamples. Convex transaction subtransactions and session request outcomes
support the existing Core root, atomic success storage and callback-free replay.
This slice selects no new Core algorithm. Existing native root participation,
scope exclusion and durable event delivery differences remain applicable.

Native HTTP uses callable Remote Query for both Cart refetch and publishable-key
Sales Channel scopes. The Cart creation graph already owns Product local taxonomy,
Customer Groups, Region Countries, native Cart totals and Payment Session paths.
Admit the complete requested projection before creation; never create a Cart and
then discover an unsupported response profile. Refetch remains a separately
protected read after native settlement.

The shared framework Fetch adapter now honors `req.errors` before invoking the
next middleware or route, matching native Express `wrapHandler`'s HTTP 400
envelope. Cart's pinned key/channel middleware records refusals there. The
framework regression preserves the previous mismatch, which returned 200
instead of 400. Sales Channel authorization remains with the native middleware;
the pinned comparison source is unchanged.

The full default projection witness exposed native read metadata gaps. Native
Cart totals and Promotion application-method relations stay with their module
owners. A focused independent peer challenge traced native Remote Query parsing,
expansion and MikroORM serialization: bare `items.variant` creates no expansion
and its absent value is omitted; the bare Product selection is redundant beside
its genuine nested fields. Native Address DML has no `region_code`, and the driver
omits that field. Nested graph paths therefore reuse the existing bounded
optional-leaf projection contract with exact module-owned names. No wildcard,
nonexistent stored column, fabricated value or general unknown-field filtering
is introduced. Genuine stored fields still require complete evidence.

## Ownership and acceptance

- `medusa-http` owns the selected pinned handlers, middleware and schemas,
  manifest, source provenance and Effect HTTP host.
- `medusa-framework` owns the shared Fetch request-error boundary.
- `medusa-adapter` owns native runtime construction, the authenticated source
  catalog, workflow dispatch, callable Remote Query, complete graph admission
  and request scopes. The application DO remains a host adapter.

The bounded profile preserves verified Customer selection, guest behavior,
publishable-key revocation, single/multiple channel behavior, native validation
and missing-Cart response,
default and selected fields, totals and relations, one Cart/event outcome, late
failure rollback, reconstruction and drained cleanup. PGlite and ordinary-role
PostgreSQL establish these connected behaviors separately; the actual Workerd
application DO supports create/retrieve across recreation. Other Cart mutations,
checkout HTTP, transport-loss retry, performance measurement and mixed
Application/native deployment remain separate gates.
