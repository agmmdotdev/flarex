# Application and Product private atomic attempt

Status: **proposed for scope agreement; runtime implementation has not begun.** This is the first connected package in the [mixed core roadmap](./README.md). The [mixed mutation design](../../design-notes/flarexdb-mixed-mutation-execution.md) remains a proposal; the [accepted database design](../../design-notes/flarex-db-accepted-design.md) governs until the focused execution-profile change below is agreed. This preflight records a scope proposal, not test results.

## Coherent outcome and exact Product graph

Through the genuine sandbox, executor and trusted host boundary, one private native mutation creates an Application `productLaunch` row, calls native `ProductModuleService.updateProducts(productId, { title, handle, status: "published" })`, retrieves the pending Product, lists Products by the **new handle**, and patches the launch using returned Product values. Seed existing Product fixtures with nonempty options, option values and tags and relevant variants, images and categories so the selected native replacement path must preserve them. The handle list proves pending index membership; the retrieve proves the new title and status. A status list predicate is outside this admission because the current Product query profile supports `id`, `handle`, `collection_id` and `type_id`, not status. `q` and other text/JSON search reads inside the attempt are excluded. Maintain and check the changed title's search entry after commit without claiming snapshot search support.

This scalar-input native update is not a scalar-only implementation. [ProductModuleService.updateProducts](../../packages/medusa-product/src/services/product-module-service.ts) first retrieves the original by ID, then hydrates `options`, `options.values` and `tags`, normalizes and validates, and calls `upsertWithReplace` with `options`, `variants`, `images`, `tags` and `categories` relation policies. The existing [adapter command](../../packages/medusa-adapter/src/product-commands/mutations.ts) invokes the native service and the [read commands](../../packages/medusa-adapter/src/product-commands/reads.ts) invoke native retrieve/list. Preserve original relations and native result shape. Do not replace this path with direct scalar DML, a duplicate service, or a projection that discards required fields.

The root publishes one authoritative outcome: Application and Product changes, derived index/relation state, retained committed-success result and the native Product event intent. Native `updateProducts` has `@EmitEvents`; the [Product module](../../packages/medusa-adapter/src/product-module.ts) connects its event bus, and [Product local event policy](../../packages/medusa-adapter/src/product-local-events.ts) checks call receipts and the `product.updated` event. Its Medusa `MessageAggregator` context must survive borrowed participation: framework code captures the event, and only the root persists its authenticated intent at settlement. A failure after Product work leaves no committed business changes, committed-success result or published event intent; aborted journal/recovery evidence may persist. The patch must use the pending Product result; an independently committed commerce command cannot supply it.

Use private host bindings for proof. Public `ctx.commerce`, SDK/configuration/generated types, Payload hooks, workflows, external effects, arbitrary Product methods and hosted activation are outside this first package.

## Why now and authority amendment

The existing Application journal supplies exact-attempt identity, ordered syscalls, sealing, OCC, retained outcome and recovery. The shared logical working set supplies Product pending/query/constraint mechanics, but its constructor borrows a physical transaction and current-state reads. Neither existing profile permits an interleaved sandbox call to a real Product service under one historical snapshot and pending view. This package connects those owners and the real consumer; a helper-only milestone cannot meet its gate.

Propose an explicit **private admitted mixed logical attempt** for one authorized scope and physical placement. Upon scope agreement, amend the accepted design's separate-profile text and its table entry rejecting generic atomic `ctx.db + ctx.cms + ctx.commerce` to distinguish this narrow profile from generic/public composition. Ordinary Application OCC, supported standalone commerce commands and named atomic commands remain distinct for their real callers. A child Product call borrows the attempt and cannot settle itself. No SQL transaction spans sandbox execution, user callbacks, remote work or waits; checked reads, durable attempt/operation evidence writes and final settlement use short transactions. This is the recommended change to the accepted execution profile, not an assertion that the accepted design already permits it.

| Owner | Required first-package contract |
| --- | --- |
| Native attempt/journal | Own root request and attempt identities, ordered operation/result/dependency evidence, one canonical pending state, budgets, cancellation, replay, seal, retry and recovery. No second ledger. |
| Logical storage and Product adapter | Refactor reusable working-set evaluation for fixed historical snapshot plus pending changes. Bind the real service to an opaque borrowed manager; retain Medusa validation, normalization, relation and event semantics. |
| Read/index/constraint owners | Supply complete historical point, handle-index and required relation candidates; merge pending rows and record missing-row, membership, uniqueness and constraint decisions. Refuse unsupported queries. |
| Commit/materialization/publication owners | Revalidate authenticated Application and Product authority and all observations, settle coalesced writes, result and event intent atomically, then publish through the existing owner. An Application grant never authorizes Product writes. |

The [native journal protocol](../../packages/flarex-protocol/src/commit-protocol.ts) currently encodes Application reads/usage and `LogicalAppWriteV1[]`; the [journal store](../../packages/persistence-postgres/src/sessionJournalStore.ts) owns syscall sequence, transport replay, seal and opaque attempt handles. The [point commit owner](../../packages/persistence-postgres/src/pointCommitTransaction.ts) authenticates Application writes and validates point, range and relation OCC. The [working set](../../packages/persistence-postgres/src/logicalDocuments/workingSet.ts) currently reads through a physical transaction; its [contribution](../../packages/persistence-postgres/src/logicalDocuments/contribution.ts) checks observed rows, empty scans, unique/index/page/search membership at settlement but does not establish initial historical candidates. Extend these real owners with separately authenticated Product operation, result and dependency evidence; do not broaden Application write grants or create an adapter-owned overlay/commit path.

## Snapshot, admission, retry and recovery

- Pin scope, placement, schema/index identity, Product binding, method and event contract to the root attempt. The trusted session/grant chooses exact scope. Refuse wrong scope, stale binding, unsupported method and two-scope ambiguity before framework effects. Audit the selected host route for remaining deployment-only lookups against the [same-deployment authority boundary](../shared-logical-storage/56-same-deployment-scope-authority.md); import only corrections this proof requires.
- Read the native Product existence check, original relation hydration, unique-handle decision, retrieve and selected handle list at the attempt snapshot plus earlier pending work. Preserve the actual native evaluation and first-failure order. Historical [Application index readers](../../packages/persistence-postgres/src/appIndexEntries.ts) are reuse candidates where their exact key and predicate semantics match. Protect empty/missing results, relation membership, unique claims and changed handle membership, including a change after attempt snapshot but before the first Product read. Standalone Product writers must provide compatible history/conflict facts.
- Validate source revisions, index/range and relation membership, conditional uniqueness and constraints under the existing scope-clock and lock order. Current-only [logical search reads](../../packages/persistence-postgres/src/logicalDocuments/searchReads.ts) cannot recover a historical candidate omitted after a title change; refuse `q` rather than treating commit-time recheck as a snapshot read. A required transitive native read without complete candidates blocks at the shared owner, not at an adapter bypass.
- Admit one sequential mutable attempt. Unsupported parallel calls, external effects, locks, unbounded queries and callbacks refuse. A framework error after staged work makes the root rollback-only even if sandbox code catches it. Preserve catchable pre-effect native validation only after its exact no-staged-work boundary is proved.
- On OCC conflict, discard all pending work and rerun the **whole** sandbox mutation with a fresh attempt, snapshot and Product manager/state; root retry and resource budgets remain enforced across attempts. Revalidate pinned bindings; never reuse abandoned service state. Within one attempt, duplicate transport calls return authenticated recorded operation evidence without executing Product twice. Unknown COMMIT resolves exact durable outcome before any rerun; confirmed success returns the retained result without recapturing events. Cancellation revokes further calls and reports the durable outcome if commit raced with it.

The named durable environments and outstanding attempts have **not yet been audited**. Before activating a changed format, inventory the journal tables in [schema](../../packages/persistence-postgres/src/schema.ts), executor point-journal callers, stored-attempt authentication readers, sealed compiler/publication readers and retained-result consumers. Classify each environment's evidence and choose drain, offline conversion or exact coexistence as warranted; do not invent a reset or dual write/read path. Record affected identities and data, cutover order, validation and removal in this preflight before dependent implementation. Necessary in-scope internal breaks are acceptable after that disposition, but preserving intended recovery is mandatory.

## Challenged alternatives

- A named SQL command is appropriate for a predeclared sequence, but cannot provide sandbox branching with historical pending reads across calls. Retain its supported profile.
- Holding the current commerce transaction across the sandbox or calling an independently committing host would violate transaction lifetime or atomicity. Borrow opaque attempt participation instead.
- A Product-specific overlay, scalar-only rewrite of `updateProducts`, current-only index lookup or final returned-ID recheck misses native relations or snapshot membership. Fix the shared owner and prove it with a neutral non-commerce fixture as well as Product.
- A universal framework transaction API collapses distinct lifecycle semantics. Reuse common attempt/storage mechanics with separate authenticated domain admission.

## Validation and completion gate

The package exits only with the full private create → native update → pending retrieve/handle-list → dependent patch path and one retained outcome. Include nonempty original options/values/tags and relevant variants/images/categories from native fixtures, native result fidelity, title/handle/status change, preserved relations, postcommit search maintenance and `product.updated` intent; late failure, missing Product, wrong authority/scope, two-scope refusal, rollback-only and unsupported-path refusal. Exercise concurrent standalone Product writers and Application writers on **distinct ordinary-role PostgreSQL connections**: point conflict, empty handle membership, changed handle, relation membership, unique collision and opposing lock order. Cover a change before first framework read, transport duplicate, whole-attempt retry with fresh framework state, cancellation before/during commit, snapshot expiry, sealed finish-only recovery and unknown COMMIT with no service/event rerun.

Use real native Product/service, neutral core, journal/commit and genuine sandbox/host tests. Run PGlite for fast behavioral evidence and ordinary-role PostgreSQL for transaction, constraint, isolation, recovery and concurrency claims; report separately. Run affected typechecks/builds, source/provenance guards, `pnpm lint:core`, `pnpm lint:diff` and staged diff lint; both standing reviewers inspect the significant-code checkpoint and re-review substantive fixes. Migrate affected consumers, remove displaced internals/tests/exports/docs and resolve durable disposition before one scoped commit. A passing private proof does not imply production or arbitrary framework support.

## Decisions to close before dependent implementation

The first admitted Product update is fixed to `title`, `handle` and `status: "published"`, with pending retrieve and `listProducts({ handle: newHandle })`. Relation mutation inputs, status predicates and `q` require revised scope and proof.

1. Choose the precise mixed journal/working-set representation and the smallest schema/protocol change that preserves authenticated operation/result evidence and one pending view. Inventory durable readers and outstanding attempts before activating its format.
2. Agree the private execution-profile amendment and any exact host scope-binding correction required by this connected proof. Public APIs and the remaining shared-storage backlog stay separately gated.
