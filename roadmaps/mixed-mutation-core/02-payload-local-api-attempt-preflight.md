# Application, Product, and Payload Local API private attempt

Status: **implemented as a private isolated-scope proof.** The [first Application and Product attempt](./01-application-product-attempt-preflight.md) is also implemented only in isolated test scopes. This second slice extends that same private attempt with one pinned Payload Local API lifecycle. Named-environment activation, public `ctx.cms`, and general Payload compatibility remain separate gates.

## Coherent outcome and selected native path

Run one real sandbox mutation through its trusted host and existing journal:

1. Insert an Application launch row.
2. Call the already admitted native Product title/handle/status update and read the pending Product result.
3. Call `payload.create` for one compiler-owned `posts` document, using the pending Product title. The selected fields are required unique `title`, required `score` with default `0`, required `enabled` with default `false`, and required `publishedAt` date, as declared by the current [scalar profile](../../packages/payload-adapter/src/conformanceProfile.ts). One fixed, trusted, create-only `afterChange` hook invokes a same-request nested `payload.update` to set `score` to `1`, then `payload.findByID` to observe it.
4. Invoke an outer `payload.update` with `enabled: true`, then `payload.findByID` at depth zero. Patch the Application launch from that returned Payload document, rather than from a seed constant or a direct database adapter call.
5. Settle Application, Product, Payload, the root result, and the selected Product event intent once. Payload creates no separately committed result or event in this profile.

The [existing Payload operations](../../packages/payload-adapter/src/operations.ts) already call native `payload.create`, `payload.update`, and `payload.findByID` with `overrideAccess: false`, depth zero and a request carrying the transaction ID. This slice must preserve those calls and Payload's access, defaults, validation, hook order and returned document behavior. The pinned `payload@3.88.0` create path initializes the request transaction before access and storage, runs `afterChange` after the adapter create, then conditionally commits; its failure path calls `killTransaction`. Update-by-ID performs access and pending-document lookup before validation, adapter update, `afterChange` and conditional finalization. Find-by-ID runs access and the ID query and then `afterRead`. The exact release and source locations are recorded in the [Payload adapter contract](../flarexdb-framework-integration/preflight/07-payload-release-and-adapter-contract.md).

The current [conformance hook](../../packages/payload-adapter/src/conformance.ts) exercises nested read/create, not nested update. Add one fixed test-support profile for the create-only nested update/read. Do not install it in the [ordinary runtime composition](../../packages/payload-adapter/src/composition.ts), expose arbitrary hook registration, or let the sandbox select hook code. Payload uses the `afterChange` return as the outer create result, so the test must obtain the final score from an explicit subsequent `findByID`; it must not assume the outer create result reflects the nested update.

## Why this slice follows Product

The first slice proves one journal-backed pending view, historical checked Product reads, exact participant receipts, whole-root retry and atomic publication without holding SQL across the sandbox or native service. Payload now supplies a distinct scalar document source and real Local API lifecycle. The nearest missing end-to-end proof is that a native Payload request can borrow the same attempt, observe Product-derived input and its own nested pending writes, and leave no partial committed state when a late hook fails.

The accepted [mixed mutation design](../../design-notes/flarexdb-mixed-mutation-execution.md) requires selected Payload access, validation, nested hooks and request reuse while keeping framework policy with Payload and settlement with Postgres. The [Payload adoption roadmap](../flarexdb-framework-integration/07-payload-adoption.md) records the existing private standalone scalar host; it does not make that physical transaction host an attempt participant. This preflight selects a second connected consumer and its core correction, not a Payload wrapper around independently committed CMS commands.

The nested hook update/read belongs **inside the outer Payload operation's one accepted syscall and receipt**. It cannot reenter the root journal semaphore as an independent sibling operation, open a second pending map, or independently seal. Payload's ordinary `beginTransaction`, `commitTransaction` and `rollbackTransaction` entrypoints may be invoked by its native lifecycle, but the mixed bridge resolves them as request-local ownership and rollback-only signals under the root. No SQL transaction remains open while Payload access or hook code executes. Individual checked reads and durable operation acceptance use short transactions.

Pinned Payload also permits `req.transactionID` to be a promise of the owned ID. Resolve it under the existing request cancellation/deadline and validate the resolved nonblank ID against this live borrowed request; do not reject a valid `Promise.resolve(id)` merely for being a promise. An unresolved promise must be interrupted or drained under that same expiry, without a second deadline or alternate transaction. The borrowed mixed request requires its owned ID for reads as well as writes; the ordinary standalone read profile retains its separately checked absent-ID behavior.

Admission pins the exact scope, physical target, Application head, Payload content source/binding and configuration, selected methods, principal, fixed trusted access/hook execution profile and its revision. The sandbox may pass only selected operation arguments; it cannot provide a Payload instance, request, principal, transaction ID, hook, raw manager or finalizer. Ordinary runtime access callbacks return `true`, so their existing conformance establishes **access-stage execution**, not principal-sensitive authorization. The fixed test-support allow/deny profiles use a trusted principal to witness denial order without becoming an ordinary callback policy API.

The existing journal V2 participant operation and neutral before/after document effect envelope can carry this selected Payload scalar result, with empty Payload event intents. No V3 or SQL schema change is required for this fixed profile. Its participant binding already carries a canonical digest that final publication checks. Select an allowlisted trusted Payload participant identity incorporating the exact fixed hook/access/runtime revision digest, bind that identity to the receipt, and reselect it under the final commit authority, including finish-only recovery. A changed revision fails closed. The Payload content schema digest alone does not authenticate hook code, and this isolated fixed test profile does not authorize arbitrary hooks or production binary rollout. A later discovered durable mismatch requires a revised inventory and scope agreement before changing the format.

## Snapshot, query and failure contract

Only create, update-by-ID and find-by-ID at depth zero are admitted. The Payload title unique claim, exact ID absence/presence, defaults and repeated update of the same pending document must use the root snapshot plus earlier Application/Product/Payload work. The selected exact-ID path has a historical point reader. The scalar compiler emits a retained ordered index for required unique `title` so historical unique lookup can prove both ownership and absence; final OCC still rechecks exact ownership. A standalone Payload writer to the same selected source must preserve compatible history and conflict facts. The admitted query body must continue refusing scans, search, relations and lifecycle operations; do not accept a current-only read that could omit an earlier matching row.

The success hook may call only its admitted same-request nested update and find-by-ID. A **separate fixed, revision-pinned failure profile** performs that same nested update/read, then invokes one nested create missing the required title after both outer and nested writes have staged, catches the native `ValidationError`, and still poisons the mixed root even if the outer hook or sandbox catches it. Neither profile is a sandbox-selected mode flag. Their code and transitive dependencies are reviewed and pinned. They run as trusted Node test-support code under the same no-open-SQL-transaction rule. Remote effects, uploads, email, arbitrary hooks and sandbox callbacks are excluded. Because Payload's native create catch calls `killTransaction` and clears `req.transactionID`, the bridge must retain root rollback-only state independently of that mutable field. The hook witness must observe the caught native `ValidationError`; the root reports rollback-only after that error is caught because Payload passes only the transaction ID to `killTransaction`. An uncaught invalid create still maps to `documentInvalid`. Record available cleanup failures separately; defects and interruption retain their distinct causes. The journal/executor's current Commerce-only domain-error union and classifier must admit selected CMS errors without turning infrastructure failures, defects or interruption into expected participant rejection. No savepoint recovery is implied.

One root retry after OCC conflict discards all pending work and reexecutes the **entire** sandbox with a fresh attempt-scoped Payload instance/runtime, request and hook state, Product manager and snapshot. Within one attempt the immutable configuration may be reused, but no abandoned mutable request/dataloader state may survive. A transport duplicate returns the authenticated receipt without executing access, validation or hook callbacks again. A confirmed committed outcome returns the retained result and event intents without rerunning Payload. Cancellation must drain or revoke nested work; an unknown final COMMIT resolves durable evidence before any rerun. The same cumulative root call/byte/read/retry limits apply to nested work.

Attempt replacement authenticates the sealed participant operation and rechecks its dependency evidence under the locked root before minting a fresh attempt. A later unrelated commit can advance the scope clock without resolving the original Payload title conflict; replacement matches the exact participant and syscall and accepts a revalidated conflict at that later clock. A standalone winner of the same title remains committed, while the retried native Payload create receives its ordinary unique validation failure and leaves no mixed publication.

General `find`, `count`, filters, sort/pages, depth-one population, relationships, delete and preference cleanup, drafts/versions, globals, auth, locks, workflows and named-environment activation are outside this admission. Existing standalone support for those selected profiles does not authorize them inside the mixed attempt.

## Challenged alternatives

- Calling the current [standalone CMS host](../../packages/persistence-postgres/src/cmsTransaction/host.ts) from the sandbox would independently settle, hold a physical SQL transaction through hooks, and create a second pending authority. Retain it for its supported standalone callers and borrow the native journal for this slice.
- Calling `payload.db.*` directly skips Payload Local API access, defaults, validation and hook lifecycle. Use native `payload.create/update/findByID` through an admitted request.
- Treating Payload as Medusa relational rows, merging its content compiler with Product schema selection, or adding a universal framework CRUD registry would erase distinct source and lifecycle authority. Reuse only source-neutral mechanics and keep direct selected bindings.
- Replaying only the failed Payload child after OCC would reuse abandoned Product/Application observations. Retry the whole root. Executing hooks at final commit would alter Payload ordering and could run them under a SQL transaction; capture checked effects before acceptance and publish without callbacks.

## Validation and completion gates

Implementation pins the exact trusted Payload access/hook revision identity in the participant selector and durable binding, with selected methods, error order and nested receipt boundary as described above. The connected Worker proof must use the real native Product service and Payload Local API, not a synthetic handler or direct adapter CRUD. Prove the happy sequence above, pending Product-derived title, default `score`/`enabled`, nested update/read, outer update/read, dependent Application patch, one root result and Product event, and no SQL transaction around the hook.

On both PGlite and ordinary-role PostgreSQL, cover fixed access allow/deny, required/unique validation, wrong scope/binding/principal/transaction ID, valid promised ID, unresolved-ID cancellation, unsupported method/query/hook refusal, late caught hook failure after Product and nested Payload writes, rollback-only and no committed rows/result/event. Prove a concurrent standalone Payload title/row change and Application/Product conflict on distinct PostgreSQL connections, whole-root retry with fresh request/manager, duplicate acknowledgement without hook rerun, cancellation during nested work, sealed finish-only recovery and unknown COMMIT with retained outcome. The first slice's Product and ordinary Application regressions remain required after neutral authority migration.

Affected consumers have moved to the source-neutral participant authority, displaced mixed internals have been removed, and the private three-consumer attempt settles once. The selected native, recovery, conflict and regression gates above are proved in isolated PGlite and ordinary-role PostgreSQL scopes. A bounded proof does not establish Payload general compatibility, a public `ctx.cms` API, or hosted activation. The next Medusa workflow capability needs its own focused preflight.
