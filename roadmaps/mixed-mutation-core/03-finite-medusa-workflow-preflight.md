# Finite Medusa workflow in the private mixed attempt

Status: **proposed for scope agreement; no runtime implementation is approved by this preflight yet.** The [Application/Product](./01-application-product-attempt-preflight.md) and [Payload Local API](./02-payload-local-api-attempt-preflight.md) slices are implemented only in isolated scopes. This third package extends their one journal-backed root; it does not activate a named environment or expose an authoring API. The [mixed execution design](../../design-notes/flarexdb-mixed-mutation-execution.md), [accepted database design](../../design-notes/flarex-db-accepted-design.md) and [mixed roadmap](./README.md) govern authority and completion.

## Coherent outcome and exact selected graph

Run one private catalogue-launch mutation through the existing real sandbox, executor and trusted host. Seed a Product with option `Size` and value `0`, and an **already attached** Product Tag with value `preview`. The root creates an Application `productLaunch`, uses the admitted native Product title/handle/status update and selected Payload `posts` create, nested update/read and outer update/read, and uses their returned values in a dependent Application patch. Inside that same root, invoke one ordered parent Medusa workflow with two genuine `runAsStep` children:

1. The [selected `productVariantPricingWorkflow`](../../packages/medusa-adapter/src/product-variant-pricing-workflow.ts) creates **one** Product Variant with `Size: "0"`, **one** PriceSet with **one USD base Price**, and the stored Variant–PriceSet Link. Its real native `createProductVariantsStep`, `createPriceSetsStep`, `createVariantPricingLinkStep` and `useQueryGraphStep` remain the business operations. Read pending Variant, PriceSet, Price, PriceRule and Link graph results. The base Price has no price rules in this fixture; the PriceRule read must return an empty collection with correct pending graph semantics. This selected Flarex-authored native-step composition is **not** the full upstream Product or variant workflow.
2. The exact promoted [native `updateProductTagsWorkflow`](../../packages/medusa-core-flows/src/product/workflows/update-product-tags.ts) selects the preattached tag by ID and changes `preview` to `launched`. Read `Product.tags` within the same pending view after this child. Its native update step, hook location and workflow event remain intact. Register **no hook callback** for this profile: the native hook point exists, but no arbitrary or user callback is admitted.

The parent is an ordered definition with one immutable revision and explicit child identities, input/output codecs, method/query permissions, hook selection and event policy. Register Product **once** with `createProductVariants`, `listProductTags`, `updateProductTags` and its graph; Pricing with `createPriceSets`; Link with `create`. The Product graph permits `id`, `title`, `tags.id` and `tags.value`; Pricing and Link reads use their separate graph roots, with no invented cross-module hydration. The parent contributes Product, Pricing and Link source effects to **one** existing root outcome, alongside Application and Payload. The first child alone produces module events but no external workflow event; the tag child supplies a real native child frame and a checked `product-tag.updated` workflow event without adding a fourth source. Expect one ordered transcript and one commit's Application, Payload, Product/Pricing/Link rows, retained result, module event intents and native workflow event intent. Late failure after either child leaves no committed business rows or event intents.

The [existing pricing test](../../packages/medusa-adapter/test/logical-product-variant-pricing-workflow.test.ts) proves the selected standalone graph over logical storage, including stored Links, pending graph reads, event cardinality and generated IDs. The [tag composition test](../../packages/medusa-adapter/test/product-tag-composition.test.ts) proves native child frames, hooks/events and sticky refusal under the independently settling host. Neither proves that `host.run` can execute within a mixed attempt. The pinned [upstream `createProductsWorkflow`](../../third_party/medusa/upstream/packages/core/core-flows/src/product/workflows/create-products.ts) and [createProductVariantsWorkflow](../../third_party/medusa/upstream/packages/core/core-flows/src/product/workflows/create-product-variants.ts) still transitively select broader Link/Inventory work even when caller inputs look narrow. This package deliberately selects the already exercised Pricing branch and the exact tag update instead of claiming full upstream Product admission.

## Why this package now and boundaries

The implemented Product/Payload root already has snapshot-plus-pending evaluation, ordered durable receipts, whole-root retry and one settlement. The missing connected proof is that a finite native workflow can borrow that authority across **several** genuine logical sources, expose its own intermediate graph results, and record both event families without its own commit. The current [workflow host](../../packages/medusa-adapter/src/workflow/host.ts) calls an independently settling `host.run`, while the [journal operation](../../packages/persistence-postgres/src/sessionJournalStore.ts) authenticates one source binding and one source's effects per syscall. Calling the standalone workflow host inside the root would create a second settlement; making each child a recursive journal syscall while the outer invocation marker is live would violate the root's in-flight/replay contract.

The admission is one fixed, sequential, database-only parent and its two named children. No full Product/Inventory workflow, generic WorkflowManager or LocalWorkflow scheduler, parallel steps, waits, remote effects, resource locks, arbitrary hooks, text/`q`/JSON search, price calculation, public APIs, hosted activation or performance optimization is included. In particular, creating a base Price and Link does **not** prove a calculated price read. Unsupported steps, callbacks, queries and event names fail closed before effects or poison the root if discovered during a child.

## Replay, conflicts and recovery

- Generated native IDs and time values are provisional **per attempt**. An authenticated duplicate transport call returns the exact recorded operation result; a confirmed committed replay returns the exact retained root result without regenerating IDs, time, steps, hooks or events. A logical OCC restart discards the entire attempt and reruns the whole sandbox and parent with fresh frames, IDs and time; all dependent Application/Payload references must be recomputed from the new outputs. Caller-supplied stable IDs remain exact inputs and retain normal conflict/uniqueness behavior. No generic determinism engine or precommit external publication is introduced.
- A live invocation marker rejects/waits for duplicate execution. After expiry the existing execution claim and attempt lease decide abandonment, with fresh whole-root retry only after exact outcome resolution. A failed child or event/graph validation makes the root rollback-only even if native code catches the error. Cancellation joins/cuts off owned callbacks, closes the borrowed context and reports an actually committed result if it raced with settlement.
- A lost or ambiguous COMMIT acknowledgement resolves journal, commit and retained-result evidence **before** any callback rerun. Finish-only recovery verifies the same workflow revision, ordered source bindings, frame identities, receipt hashes, dependency/effect/event correlation and committed output. A binding/activation change refuses rather than silently switching the admitted graph during retry or recovery.
- Transaction-covered native compensators do not run to undo provisional database work that the root rolls back. A required compensator for an external effect would make that step unsupported here. No independent child retry or compensation transaction is admitted.

## Breaking contracts, durable data and cleanup

The V2 format is genuinely single-source: its `AdmittedParticipantBindingV1` hashes one `participant`/`method`/`sourceKey`/binding head, its `AdmittedParticipantOperationV1` stores one source and flat effects, and the [journal schema](../../packages/persistence-postgres/src/schema.ts) checks `journal_format = 'flarex.session-journal-v2'`. The receipt primary key has one row per syscall sequence and V2 normalization disallows duplicate participant operation sequences, so several V2 source operations cannot safely represent one outer invocation. V3 therefore requires an explicit protocol, syscall request/outcome codec, receipt binding/correlation, canonical seal and commit-plan change. The existing opaque receipt bytes and write-event bytes/ordinal columns may hold one authenticated aggregate workflow receipt and flattened effects without a new table, but the exact V2 journal-format CHECK **must change through a structural migration**. Receipt request/outcome codec columns are also constrained to version 1, and write events to event codec 1: assign new exact versions to changed request/outcome shapes and, if event source attribution changes its bytes, the event format; migrate their CHECKs and every reader together. This includes **Application-only** V2 journal roots, codecs and fixtures with empty participant contributions, alongside Product/Payload roots; there is no parallel mixed-only reader to retire in isolation. Before runtime implementation, inventory the exact V2 writers/readers: session admission, `operation_invoking` marker and receipt, pending point/write-event children, canonical seal/decoder, executor host/syscall transport and stored-attempt authentication, Application session finish and retained outcome, point commit validation, retry/replacement and finish-only recovery. Do not guess that a type change alone is enough or add speculative new columns.

The named-environment inventory must include `fx_system_tx_session`, `fx_system_tx_journal`, receipts, point/index/relation/write-event children, execution claims, idempotency, commit facts, result and event intents, plus outstanding attempts and all readers/writers. No named environment has been audited or activated for this private profile. **For the private V3 proof, use a fresh isolated database/schema with no V2 journal rows and a structural V3 CHECK migration.** Any existing database carrying V2 rows fails the migration precondition; merely finishing active attempts is insufficient while sealed journals/outcomes remain. Before named activation, choose and verify an explicit drain and retained-data disposition, or a separately scoped offline conversion that preserves recovery and durable outcomes, plus named source upgrades (including Payload's index/digest change). Atomic schema/code rollout must reject V2 rows until that disposition is proven. No dual reader or silent reset is authorized by this preflight. A material named-data migration decision returns to focused scope agreement before implementing that decision.

| Existing path | Disposition in this package |
| --- | --- |
| Direct mixed Product/Payload V2 participant envelope and singular issuer/commit assembly | **Replace** with V3 general ordered envelope; migrate exact private callers and tests, delete displaced mixed-only exports/codecs and duplicate assembly after replacement proof. |
| Standalone Medusa atomic workflow `host.run` | **Retain** for current independently committed workflow callers; it remains a distinct supported execution profile, with the existing SDK runner and resource/event mechanics shared where possible. Reassess retirement only after named callers migrate. |

| Journal point overlay, working-set historical readers, scope-clock publication and committed recovery | **Extend** only the multi-source evidence and V3 readers needed here, migrating in-scope callers and removing displaced mixed paths. Keep their one-authority semantics. |
| Old named V2 roots and outcomes | **Retain pending explicit data disposition**; they cannot be reinterpreted as V3 or deleted. The removal gate is a named-environment audit and validated cutover. |

## Decisions for focused scope agreement

1. Admit the fixed two-child parent described above with exact Product/Pricing/Link calls, one Variant/PriceSet/USD base Price/Link, empty native tag-hook registration, selected graph reads and both checked event families. Keep unsupported steps and broader upstream graphs closed.
2. Use one outer invocation marker and aggregate V3 receipt with ordered, individually authenticated source contributions. Version changed request/outcome/event formats, update the coherent physical constraints and all Application/framework/recovery readers, and remove displaced V2 runtime paths after their data disposition. Retain the journal as the only durable pending overlay and settlement owner.
3. Add one trusted `medusa.workflow` selector to the executor's bounded set of three selectors, bound to exactly Product, Pricing and Link source definitions; the root then has four framework sources including Payload. No synthetic merged source or caller-configured registry.
4. Prove V3 in a fresh isolated database with no V2 journal rows and fail closed on an existing V2 database. Named-environment cutover awaits an explicit retained-data and outstanding-attempt decision. Keep current finite deadlines and aggregate budgets, refusing overrun without increasing ceilings.

## Validation and exit gate

First prove a neutral three-source fixture through the same core V3 path, then the real connected Worker mutation with Application, native Product, Payload Local API, the two SDK child frames, Pricing and Link methods, pending graph/`Product.tags` reads, dependent Application patch, exact root output and one commit's module and workflow event intents. Verify that the `Size: "0"` option permits the Variant, the tagged Product relationship existed before update, and the stored Link joins exactly the returned Variant/PriceSet. Check empty PriceRules rather than implying rule creation or calculated pricing. Reject wrong workflow revision, scope, source head, principal, method, graph field, event name/group, child order, hook registration and forged/duplicate/omitted contribution before settlement.

Exercise late failure after both children and after Payload work, caught child refusal, rollback-only, transport duplicate while invoking and after receipt, whole-attempt conflict retry with fresh IDs/frames and dependent references, cancellation while a child is pending, snapshot expiry, finish-only recovery and lost COMMIT acknowledgement with no committed callback/event replay. Audit selected point, unique, relation and indexed historical reads against concurrent **standalone** Product/Pricing/Link/Payload/Application writers. In particular, native Variant creation reads Product options/values and existing variant combinations: race an option-value removal or duplicate `Size: "0"` combination. Race a standalone Link create for the same Variant–PriceSet pair; the stored rich Link's active-pair unique claim matters, while endpoint FK protection must not be assumed. Race the tag's point value change or another tag claiming `launched` under its active unique index; check `Product.tags` relation-membership change where an admitted standalone writer can make it. Use explicit IDs for controlled conflicts and a generated-ID case for replay. Verify same-scope lock order and no transaction across callbacks. `q`, text/JSON search and resource locks remain rejected, so they need no invented historical-search or lease proof in this package.

Run focused native, neutral core, protocol/journal/commit, executor/Worker and three-consumer tests on PGlite and an ordinary-role real PostgreSQL lane with distinct connections; keep their claims separate. Run affected typechecks/builds, pinned-source/provenance guards, `pnpm lint:core`, `pnpm lint:diff`, exact staged diff lint, and both standing diff reviewers, rerunning after substantive fixes. Inspect actual persistent schema/DDL before declaring V3 migration complete. Migrate affected callers, remove displaced mixed internals/tests/exports/docs and make one scoped commit only after the connected proof is green. Private correctness does not establish arbitrary workflows, hosted scale, production activation, calculated prices or public APIs. Measurement and optimization remain the next package.
