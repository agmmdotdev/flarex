# Shared Storage Completion Plan

Status: active, with owner standing approval for implementation and necessary
breaking changes. This is the successor to the completed core execution goal.

## Scope And Authority

Complete shared logical storage and structural installation/evolution ownership
for Application, Payload and existing Medusa consumers. Keep their execution
profiles and business behavior distinct. Correct shared owners, migrate consumers,
preserve behavioral coverage and remove displaced paths within each medium-sized
slice. Record preflights and material decisions; do not wait for repeat approval.

New unrelated framework capabilities, general populated-data conversion/upgrade
orchestration, developer APIs and hosted activation remain outside this goal.
Never silently reset named durable environments. Platform physical upgrades
remain distinct from logical schema evolution.

## Current Implementation

- Joint authenticated candidate composition/admission is implemented, including
  Application identity, Payload read-only views and full Product definitions.
  It grants no serving authority or generic-commerce execution.
- Application/Payload content uses generic row/index/unique/edge families.
  CMS ID and complete flat unique-key selections now use point/slot reads and
  exact settlement decisions, including pending membership and scan interleaving.
  Ordinary scalar and compound Payload declarations now execute equality prefixes
  and numeric ranges through shared indexes with pending membership and exact
  settlement validation. Complete page/count membership remains bounded. The
  selective-query package continues with representative Pricing and exact constraints.
- Multiple required-text and compound scalar Payload unique declarations now
  execute through shared constraint definitions, build/readiness and claims.
  [Compound uniqueness](./07-payload-compound-uniqueness.md) covers native error
  projection, pending key reuse and concurrent settlement. Nullable/conditional
  uniqueness remains a subsequent shared-core contract.
- Private logical indexes now carry an authenticated exact-decimal projection
  through analysis, build, write maintenance and Application indexed pending reads.
  [The decimal contract](./06-exact-decimal-indexes.md) preserves source text and
  uses existing shared index bytes. This is an ordered-value prerequisite;
  calculated Pricing, conditional unique constraints and commerce cutover remain.
- Existing Medusa models still use physical relational artifacts and installation
  evidence. Exact numeric presentation, native Links and current workflow tests
  are replacement obligations, not generic query proofs.
- Core execution, materialization, admission integrity and scoped host lifetime
  are implemented. Reuse these owners; do not reopen completed work without a
  connected defect or changed replacement contract.
- Framework installation and Application evolution remain distinct. Generated
  commerce and Payload preference storage still consume framework evidence;
  their migration and recovery obligations must move before table removal.

These packages may require more than one coherent implementation slice. They
are not five turns or permission for helper-only turns. Real consumers run as
capabilities land. Every slice includes cleanup, affected typechecks, focused
PGlite and ordinary-role PostgreSQL evidence, both read-only reviews and a scoped
commit. Final retirement audits incremental cleanup rather than postponing it.

## Completion Decision

The goal is complete only when the selected replacement executes through real
consumers, existing affected callers have moved, cross-framework/query/constraint
proofs pass and displaced commerce storage and structural migration paths are
removed. A remaining system owner requires a specific continuing responsibility;
an unmigrated required commerce consumer is not a completed cutover. Generic
families alone do not prove indexing, migration consolidation or capacity.

The detailed semantic gates remain in [query and constraint acceptance](./02-query-and-constraint-acceptance.md)
and the [domain roadmap](./README.md). Advanced evolution follows its existing
[deferred contract](./deferred-framework-schema-evolution.md).
